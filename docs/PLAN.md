# Hoke: план разработки и самостоятельной работы

Дата: 27 октября 2026. Имя npm-пакета: `hoke`, импорты через `hoke/kv`, `hoke/react`, позже `hoke/db`, `hoke/testing`.

## 1. Цель и критерий успеха

Построить полезную open-source библиотеку хранения данных для веба и React Native с общим Rust-ядром для режима DB. Проект должен показывать инженерную работу: ясные контракты, восстановление после сбоев, измерения, проверяемые ограничения, архитектурные решения.

Два режима:

- KV: настройки, флаги, небольшой кэш; localStorage в вебе, позже адаптер MMKV в React Native.
- DB: упорядоченные ключи, диапазоны, транзакции и подписки на собственном LSM-движке; обычные файлы в Rust, OPFS в Worker, позже файловая система React Native.

Не заявлять первенство, превосходство над конкурентами или гарантии надёжности без воспроизводимых доказательств. React Native и одновременный доступ из нескольких вкладок не входят в первые релизы. Синхронизация с сервером, SQL и шифрование вне текущего плана реализации.

## 3. Как принимаем решения и не останавливаемся на каждом шаге

Пользователь разрешил параллельных агентов и самостоятельную работу по плану.

Самостоятельно:

- читать и менять код, писать тесты, исправлять найденные ошибки;
- выбирать внутренние имена, разбиение модулей, детали тестов и сборки;
- добавлять необходимые для текущего этапа инструменты проверки и предусмотренные зависимости;
- менять ещё не опубликованный API, если это нужно для корректного контракта, с обновлением примеров и документации;
- проводить локальные измерения, готовить CI и файлы релиза;
- интегрировать работу агентов и повторять проверки после существенных исправлений.

Не превращать каждый завершённый пункт в вопрос «продолжать?». Внутри текущего этапа переходить к следующей доступной задаче. Обновлять журнал фактических результатов и сообщать существенные выводы.

Обращаться к пользователю, когда:

- необходимы учётные данные, права или выбор владельца внешнего ресурса;
- нужно опубликовать пакет, сайт или выполнить внешнее необратимое действие;
- меняется продуктовая цель, добавляется не предусмотренный этапом крупный объём или обязательство поддержки;
- требуется изменить уже выпущенный формат данных или публичный контракт несовместимым образом.

Для крупного архитектурного решения сначала подготовить ADR с альтернативами, компромиссами и рекомендацией. На ранних обратимых решениях выбирать рабочий вариант и продолжать; решения, задающие долговременный формат файлов и гарантии durability, фиксировать до реализации и отдельно обсуждать при переходе к Rust.

Этапы ниже не запускаются все сразу. Этапы A и native B реализованы; итоговый аудит завершён. Текущий рубеж — этап C: C1 (WASM/Worker/OPFS WAL-only), C2 (bounded scan/byte collections), C3 (commit subscriptions) и C4 (cancellation) реализованы, остальные возможности C остаются впереди. Актуальный статус — PROGRESS.md. Последующие этапы представлены как последовательные рубежи; перед началом каждого сверяем результат и ограничения, а не спрашиваем разрешение на каждую функцию.

## 5. Этап A — v0.1: завершить KV и реактивные сторы

### A1. Контракт KV и snapshots

- Сохранить синхронный контракт get/set/delete/subscribe.
- Явный выбор backend; недоступность localStorage вызывает ошибку, без fallback.
- Подписчики вызываются после успешной записи; отказ записи не выглядит успешным изменением.
- Стабилизировать ссылку результата localStorage при неизменной исходной JSON-строке. Это необходимое условие useSyncExternalStore.
- Не скрывать внешние изменения бессрочным кэшем: читать актуальную строку из backend.
- Не раздавать устаревший кэш после ошибки чтения или повреждения JSON.
- Зафиксировать семантику объектов и ограничения immutable-use в документации.
- Межвкладочные события пока не реализовывать и явно указать это ограничение.

Готово, когда: повторный get объекта стабилен; изменение сырой записи обнаруживается; сбои не отдают старые данные; старые тесты проходят.

### A2. Определения и экземпляры сторов

Публичная форма:

```ts
const settings = defineStore({
  key: "settings",
  version: 2,
  defaults: () => ({ theme: "system" }),
  validate: isSettings,
  migrations: { 2: migrateV1ToV2 },
});
const store = createStore(kv, settings);
store.getSnapshot();
store.getServerSnapshot();
store.set(nextValue);
store.update((previous) => nextValue);
store.reset();
store.subscribe(listener);
```

- defaults — фабрика, чтобы экземпляры не разделяли случайно изменяемый объект.
- В KV сохраняется одна запись `{ __stowtree: 1, version, value }`.
- Версия схемы стора отличается от маркера формата envelope.
- Runtime-валидатор проверяет текущую схему. Не считать TypeScript проверкой сохранённых данных.
- Отсутствие записи отдаёт стабильные defaults, без неявной записи при чтении.
- set/update проверяют данные и пишут envelope одной операцией.
- reset удаляет запись и возвращает defaults.
- getSnapshot стабилен до изменения данных; getServerSnapshot отдаёт стабильные defaults для SSR.
- События изменений идут через KV; два стора над одним экземпляром KV видят обновления.
- Недопустимые defaults, envelope, версии и значения приводят к явным ошибкам.

Готово, когда: контракт покрыт тестами, нет скрытых записей при обычном чтении defaults, подписки и snapshots пригодны для React.

### A3. Миграции

- Положительные целочисленные номера версий.
- `migrations[n]` переводит версию n-1 в n, без пропуска промежуточных шагов.
- Миграции синхронные; Promise/thenable явно отклоняются.
- Все преобразования выполняются до записи; конечное значение проверяется текущим валидатором.
- После успешной цепочки сохраняется один envelope, а не промежуточные версии.
- Отсутствующий шаг, исключение или невалидный результат сохраняют исходную запись.
- Сохранённая версия выше версии кода вызывает явную ошибку; downgrade автоматически не выполняется.
- Повторное открытие уже мигрировавшего стора не запускает цепочку снова.
- Пользовательские миграции должны быть чистыми: не менять исходный объект и не выполнять внешние записи. Защиту от мутации и корректность при отказе записи проверить отдельно.

Готово, когда: тесты показывают успешную цепочку, повторное открытие, missing step, future version, исключение, мутацию и отказ конечной записи.

### A4. React

- `hoke/react`: `useValue(store)` и `useStore(store, selector, isEqual?)`.
- useSyncExternalStore; стабильные snapshots, подписки и server snapshots.
- По умолчанию сравнение результата селектора через Object.is.
- Обновление невыбранного поля не перерисовывает потребителя.
- Проверить изменение selector/store, unmount и очистку подписок, несколько компонентов, SSR.
- React — peer dependency только для React entry point; runtime KV не зависит от React.
- Не добавлять useQuery/useLiveQuery и будущие DB-хуки в v0.1.

Готово, когда: тесты доказывают корректное обновление и отсутствие лишних рендеров по селекторам, SSR работает, KV импортируется без React.

### A5. Демо и объяснение API

- Пример с настройками: defaults, сохранение, reset, подписки.
- Показать миграцию старой записи и явную ошибку future version.
- Объяснить в README разницу KV/backend/store/hook и границы гарантий.
- Дать короткую последовательность запуска и проверяемые сценарии.
- Не превращать демо в отдельное большое приложение и не делать дизайн обязательным условием релиза.

### A6. Проверки и подготовка релиза

- Проверить exports, declarations, содержимое tarball, отсутствие тестов и исходных приватных файлов в публикуемом пакете.
- Из временного потребителя проверить установленный tarball, а не только workspace symlink.

## 6. Этап B — Rust-ядро на обычной файловой системе

Перед кодом: ADR для формата ключей/значений, WAL и SSTable, порядка commit/fsync, границ транзакций и поведения при повреждениях. Сравнить 2–3 варианта значимых решений.

### B1. Контракт движка

- Byte keys/values, определённый порядок сравнения и границы диапазонов.
- Storage trait и различие read/write/flush/sync; без привязки к браузеру в ядре.
- Определить put/delete/get/scan, lifecycle open/close, ограничения размеров и ошибки.
- Изолировать коды ошибок движка от ошибок биндингов.

### B2. WAL и восстановление

- Версионированные записи, длина, контрольная сумма, sequence number, tombstones.
- Протокол подтверждения записи: точно описать, когда данные считаются сохранёнными.
- Повторное открытие восстанавливает подтверждённые операции.
- Отличать оборванный хвост WAL от повреждения внутри журнала.
- Тесты обрыва на границах записей и между write/flush/sync.

### B3. Memtable и SSTable

- Упорядоченная memtable, порог сброса, immutable memtable.
- SSTable: блоки, индекс, checksum, metadata; bloom-фильтр только с тестом отсутствия false negatives.
- Manifest и безопасное включение новых файлов; никакого удаления старого файла до публикации нового состояния.
- Range scan объединяет версии и учитывает tombstones.

### B4. Compaction

- Сначала простая измеримая стратегия, с ADR о компромиссах.
- Правила выбора файлов, устранения старых версий и безопасного удаления tombstones.
- Ограничение памяти и временного дискового пространства.
- Отказ compaction не теряет подтверждённые записи.

### B5. Транзакции и тестирование отказов

- Сначала атомарный write batch; интерактивные транзакции — только после определения изоляции и конфликтов.
- Несколько ключей фиксируются и восстанавливаются как единое целое.
- Model-based тесты против эталонной упорядоченной map.
- Детерминированный сбой по seed на операциях Storage.
- Отдельные тесты с убийством дочернего процесса во время записи и повторным открытием.
- Разделять симуляцию process crash и гарантии при потере питания.

Выход B: Rust CLI/пример и тестируемый движок на файлах, документированная durability, воспроизводимые recovery-тесты. Без заявления production-ready.

## 7. Этап C — WASM, Worker и OPFS

- Подготовить WASM-сборку ядра и типизированный протокол сообщений.
- Синхронные OPFS handles открываются внутри Worker; JS API асинхронный. C5a: существующий SST v1 codec доступен WASM и внутреннему OPFS file layer; candidate create/open/lookup/scan/close реализованы без root publication. Пользователь выбрал один контейнер с журналом commit (направление B ADR0014), конкретный codec/recovery — следующий срез; реализация примитивов — ADR0015. C5b добавляет streaming merge до64 SST с сохранением tombstones и source files (ADR0016), без переключения authoritative root. C5c добавляет общий get/scan живого WAL поверх SST и единый WASM initialization (ADR0017).
- `openDB(name)` с проверкой возможностей, явными ошибками и закрытием ресурсов.
- Единственный владелец БД на первом этапе; второе открытие получает ясную ошибку.
- Версионирование протокола, отмена/таймаут, завершение Worker, обработка неожиданных исключений. C4: structural DBAbortSignal, pre-abort без dispatch; после dispatch abort завершает всю сессию/all pending с ABORTED, исход mutation может быть сохранён, без retry. Signal open действует только до ACK; cleanup предшествует callbacks. Решение — ADR0013.
- get/put/delete/scan с лимитами, prefix/range/reverse; тестирование границ и бинарных ключей.
- `collection(prefix)` с безопасным кодированием префикса и типизацией.
- Подписки на ключи и диапазоны только после commit, с тестом фильтрации по изменённым ключам.
- Миграции DB внутри атомарной транзакции после реализации необходимой семантики.
- Браузерные integration-тесты reload/crash/quota/unsupported environment.

Выход C: веб-демо с реальным OPFS, сборка и примеры, явно описанные поддерживаемые браузеры и ограничения.

## 8. Этап D — доступ из нескольких вкладок

- ADR: SharedWorker против выделенного лидера + Web Locks; проверить совместимость целевых браузеров.
- Один владелец файлов; маршрутизация запросов от вкладок.
- Передача лидерства, закрытие вкладки, пробуждение, потеря связи, устаревшие ответы.
- Последовательность commit и уведомлений; отсутствие дублей и ложных подтверждений.
- Тесты двух и более вкладок, падения лидера во время записи и восстановления.

Выход D: воспроизводимые multi-tab тесты и документированный протокол владения, без split-brain.

## 12. Параллельные потоки текущего этапа

| Поток          | Владение                                        | Задача                                                             |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| Агент A        | `src/store.ts`, `src/store.test.ts`             | Сторы, версии, миграции, ошибки, snapshots                         |
| Агент B        | `src/kv/local-storage.ts`, его тесты            | Стабильные snapshots без скрытия внешних изменений                 |
| Агент C        | `src/react/**`                                  | React-хуки, selectors, SSR и тесты по контракту Store              |
| Основной агент | package/config, docs, examples, CI, integration | Общие решения, зависимости, exports, демо, проверка всех изменений |

Агенты работают в общей папке. Каждый меняет только свои файлы, сообщает предположения и не перезаписывает чужие изменения. Нельзя объявить этап готовым по одному отчёту: основной агент читает результаты, интегрирует их и запускает общие проверки.

## 13. Definition of Done для каждой задачи

- Поведение реализовано и описано на уровне публичного API.
- Проверены релевантные крайние случаи и отказы, а не только happy path.
- Нет скрытой потери данных, silent fallback и ложных обещаний.
- Сборка, типы и относящиеся к задаче тесты проходят; после интеграции проходят общие проверки.
- Документация и пример соответствуют коду.
- Неисполненные проверки и ограничения записаны явно.
- Никакой автоматической публикации, секретов в репозитории или добавления функций следующего этапа под видом завершения текущего.
