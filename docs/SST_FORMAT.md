# Экспериментальные SST и manifest v1

Формат WAL v1 сохранён без изменений. Database работает с отдельным каталогом, Engine по-прежнему может открыть один старый WAL. Автоматического переноса между этими API нет.

## SSTable

Неизменяемая отсортированная таблица изменений. В одном файле ключ уникален, порядок — лексикографическое сравнение bytes. Значение может быть tombstone; это отличается от пустого значения. Таблицы разных поколений могут содержать один ключ: побеждает самая новая таблица или memtable.

Все числа little-endian, CRC32 IEEE как в WAL.

Заголовок 32 байта:

| Offset | Размер | Значение                     |
| ------ | ------ | ---------------------------- |
| 0      | 8      | Magic STOWSST + нулевой байт |
| 8      | 4      | Версия u32 = 1               |
| 12     | 8      | Число записей, u64           |
| 20     | 8      | Offset начала индекса, u64   |
| 28     | 4      | CRC32 байтов заголовка 0..28 |

Записи начинаются с offset 32 и используют тот же frame encoding, что в WAL v1. Sequence — порядковый номер записи внутри SST, от 1 до N; это не глобальный commit id. Put хранит значение, delete — tombstone. CRC проверяется по тем же правилам. Ключи и значения ограничены 64 KiB и 16 MiB.

Индекс: N записей `[key_len:u32][key bytes][record_offset:u64]`, затем CRC32 всех байтов индекса. Индекс находится в конце файла, CRC занимает последние 4 байта. Максимум 1 000 000 записей, максимум 64 MiB байтов индекса без CRC.

При open проверяются header/version/CRC, размер индекса до allocation, CRC индекса, строгая сортировка ключей, offsets и непрерывность records. Фиксированные record headers проверяются сразу, values не загружаются. Get ищет ключ бинарным поиском, читает нужный frame и проверяет полный CRC, ordinal и совпадение ключа с индексом. Повреждение не вызывает fallback к старому значению.

Индекс содержит каждый ключ и хранится в памяти. Sparse index, блочный layout, bloom-фильтр и compression не реализованы. При открытии есть линейный проход по индексу и record headers. Это намеренно простой первый формат, без обещания эффективности уровня RocksDB.

## Manifest

MANIFEST определяет единственное активное состояние каталога. Все поля и CRC little-endian.

| Offset       | Размер | Значение                                                    |
| ------------ | ------ | ----------------------------------------------------------- |
| 0            | 8      | Magic STOWMAN + нулевой байт                                |
| 8            | 4      | Версия u32 = 1                                              |
| 12           | 8      | Активное WAL generation, u64 > 0                            |
| 20           | 4      | Число SST generations, u32 ≤ 4096                           |
| 24           | 8 × N  | Строго возрастающие SST generations, > 0 и ≤ WAL generation |
| После списка | 4      | CRC32 всех предыдущих байтов manifest                       |

Минимальный размер 28, максимальный 32796 байт. Count/точный размер/CRC/порядок поколений проверяются до использования. Неизвестная версия и отсутствующие referenced files — ошибка. Пустой referenced WAL не инициализируется как новая база.

## Имена и публикация

Имена: g + 20 десятичных цифр generation + `.sst`, `.wal` или `.manifest.tmp`. Например g00000000000000000002.sst. LOCK — кооперативная эксклюзивная блокировка каталога. MANIFEST — единственная опубликованная точка входа.

Поколение следующего flush выбирается выше всех существующих распознанных имён, включая orphan files. Файлы создаются через create_new; никакой перезаписи старого SST или WAL. После sync новых SST/WAL и их имён записывается и синхронизируется manifest.tmp. Atomic rename заменяет MANIFEST, затем вызывается directory sync. Старый manifest не удаляется перед rename.

После успеха flush текущая memtable заменяется пустой, а старый WAL перестаёт быть активным. Подтверждённое значение теперь находится в SST. Последующие изменения идут в новый WAL.

При ошибке flush mutation API блокируется до reopen. После неоднозначного rename/sync возможен старый или новый manifest; оба описывают целое состояние с подтверждёнными данными. Orphan files не участвуют в replay. Явные compact/gc удаляют obsolete generation-файлы только после durable manifest barrier, см. ADR 0005 и COMPACTION.md.

База без MANIFEST и с непустым каталогом не инициализируется автоматически: это может быть потерянный manifest или прерванная первая инициализация. Первая инициализация до публикации manifest ещё не принимает пользовательских записей.
