# ADR 0022: классы KV и платформенные backend

Статус: принято, 29 октября 2026. Пользователь выбрал классы для KV, название backend вместо storage, разделение web/native и отдельные папки тестов. Защищённое хранение и шифрование исключены из текущего API.

## Причина

Прежний `createKV` создавал отдельное хранилище в памяти, а localStorage подключался отдельной фабрикой. Адаптер одновременно отвечал за I/O, JSON, валидацию и snapshots. С добавлением MMKV эти правила пришлось бы повторять на двух платформах. Нужны одинаковые пользовательские операции и небольшой контракт расширения без зависимости web-сборки от нативного runtime.

## Варианты

1. Оставить фабрики и типизированные адаптеры: меньше изменений, но повторение JSON-кода и несовпадение с выбранным публичным API.
2. Один класс KV над строковым backend, платформенный resolver: одна реализация JSON/snapshots/подписок и один конструктор; при сборке различается только выбор backend.
3. KVCore и платформенные подклассы: сохраняют общий алгоритм, но добавляют наследование и несколько классов KV только ради выбора backend.
4. Единый async API для всех хранилищ: допускает AsyncStorage/Web Crypto, но меняет существующий контракт и Store ради возможностей вне текущего объёма.

Выбран вариант 2.

## Контракт и разделение

`new KV<Value = unknown>({ name, backend?, validate? })` предоставляет синхронные `get/set/delete/subscribe`. Имя обязательно. По умолчанию web использует LocalStorageBackend, React Native — MMKVBackend. Пользовательский `KVBackend` реализует `read(key): string | undefined`, `write(key, value): void`, `remove(key): void`. Все операции синхронные; ошибка I/O бросается, успешная запись видна следующему чтению.

Общий класс KV отвечает за namespace, строгий JSON, необязательный runtime validator, parsed snapshots и локальные подписки. Backend получает уже подготовленный физический ключ и строку. Generic TypeScript сам по себе не проверяет прочитанные данные. Отсутствующий ключ возвращает undefined; записывать undefined нельзя.

В `kv/kv.ts` определён единственный класс KV. KVCore и платформенных подклассов нет. Общий исходник использует web resolver; сборка native входа заменяет только этот resolver на native реализацию. Нет runtime-регистрации backend, глобального состояния выбора платформы или наследования ради default.

Публичные входы `hoke/kv/web` и `hoke/kv/native` позволяют явно выбрать платформу. Web-вход гарантирует отсутствие MMKV/Nitro в графе импортов; его следует использовать в React web приложении, в том числе в workspace рядом с React Native. Автоматический `hoke/kv` проверяет условие browser перед react-native, поэтому web-сборка React Native Web выбирает localStorage. Если сборщик не задаёт browser, web-вход выбирается явно.

`backend` принимает готовый KVBackend или карту `{ web?: KVBackend; native?: KVBackend }`. Готовый backend используется на обеих платформах. Карта выбирает только текущую платформу; отсутствующая ветка использует её default. Ошибка явно переданного backend не вызывает перехода к default или другой ветке.

`kv/web/` и `kv/native/` содержат платформенные resolver и backend. `index.ts` — только явные фасады экспорта, классы используют TypeScript private; внутренние runtime helpers не импортируют публичный фасад. MemoryBackend остаётся внутренним тестовым helper, публичного экспорта нет. Тесты KV расположены вне runtime в `packages/hoke/tests/kv/`.

Store сохраняет свой API и принимает структурный KVSource; переход на классы не требует наследования от KV. DB, Rust Storage, WAL/SST/container форматы и Worker protocol не меняются.

## Совместимость и ошибки

API ещё не опубликован: фабрики createKV/createLocalStorage заменяются классами, storage — backend, имя становится обязательным, default меняется с памяти на постоянный платформенный backend. Вызовы и примеры в репозитории мигрируют вместе.

Физические localStorage ключи `stowtree:["name","key"]` и Store envelope сохраняются. Переименование и перенос JSON-слоя не мигрируют и не переписывают существующие данные. Все backend используют строгий JSON; память больше не служит способом сохранить не-JSON значения через публичный KV.

Недоступность платформенного backend даёт ошибку без fallback. Подписчики вызываются после успешной записи; их исключения собираются после вызова остальных слушателей и не отменяют сохранение. Внешнее изменение обнаруживается чтением, но не создаёт событие в текущем KV. Кэш не скрывает ошибки чтения или повреждения JSON.

## Границы и проверка

RN KV использует react-native-mmkv и react-native-nitro-modules, которые устанавливает нативное приложение. Тест doubles проверяют адаптер и единые контракты; они не доказывают работу MMKV на устройстве. iOS/Android сборки и device tests пока не заявляются выполненными.

Не добавляются SecureKV, управление криптографическими ключами, шифрование, async backend, TTL, перечисление/очистка ключей и транзакции. localStorage и синхронное JSON-кодирование ограничивают размер полезного KV; большие наборы относятся к отдельному DB API. Фактические результаты интеграционных проверок фиксируются в PROGRESS.md.
