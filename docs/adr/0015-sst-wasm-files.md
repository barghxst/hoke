# ADR 0015: существующие SST v1 через WASM и OPFS

Статус: принято для подготовительного среза C5a. Публикация browser SST/compaction по ADR0014 ещё не выбрана. Этот срез реализует файловые примитивы; `openDB` продолжает работать в `wal-v1`.

## Решение

Переиспользуем существующий Rust SST codec вместо второго JS writer/reader. Открываем `hoke_core::sstable` для платформенных биндингов: immutable reader, потоковый writer и preflight. Формат `STOWSST\0` v1, CRC, индекс и tombstones остаются прежними. Владение storage и flush/sync/publication явно разделены.

WasmSst открывает существующий файл либо создаёт кандидата в пустом destination. Создание сначала проверяет весь вход, затем пишет существующим codec, синхронизирует файл и открывает reader. Неполный файл после I/O-ошибки не объявляется готовым. Проверка при open читает header/index/record headers; payload CRC проверяется при lookup/scan. Это не полный scrub.

Внутренний `sst-files.ts` получает каталог от вызывающего кода. Он загружает WASM до создания файлов, выбирает свободное случайное имя `.sst`, получает исключительный sync handle и удерживает его до close. Вызывающий coordinator обязан обеспечить исключительное владение каталогом на время выбора/создания: getFileHandle с create не эквивалентен create-new. Слой не выдаёт себя за native Directory.

## Передача записей

WASM принимает и возвращает временный packet: u32LE count, затем для каждой записи u32LE keyLength, u32LE valueLength, key и value. `0xffffffff` в valueLength означает tombstone без value bytes. Пустое значение отличается от tombstone и отсутствующего ключа. Lookup возвращает tag0 для missing, tag1 для deleted, tag2 с bytes для value. Packet не является новым долговременным форматом.

Вход строго упорядочен по bytes, уникален, полностью проверяется до записи: key64KiB, value16MiB, packet32MiB, максимум1M записей. Scan использует индекс для диапазона/prefix/reverse, возвращает tombstones и ограничен1000 записями/32MiB. Бюджет результата проверяется после декодирования очередной выбранной записи; дополнительно может быть прочитано до16MiB payload. Он не является ограничением всего WASM heap; построение кандидата пока материализует вход.

## Lifetime и ошибки

SstFile.close всегда пытается освободить reader и sync handle, даже если одна из стадий cleanup завершилась ошибкой. Ошибку самого handle.close скрыть нельзя: исключительный ресурс может потребовать завершения Worker. Повторный close идемпотентен. После close чтение невозможно. Ошибка открытия не создаёт отсутствующий файл и не ремонтирует повреждённый. Ошибка создания может оставить orphan; candidateName в ошибке позволяет будущему coordinator учитывать его. Автоматического удаления файлов нет.

Исключительный handle защищает один файл; это не directory lock, не root publication и не гарантия сохранения имени при потере питания. Успешный create означает завершённый кандидат с file flush, а не commit пользовательской транзакции. Существующий WAL не очищается, не переключается и не удаляется.

## Альтернативы и следующий шаг

JS реализация SST дублировала бы codec и правила CRC. Прямой OPFS адаптер native Directory пока не имеет нужного directory barrier. Поэтому этот срез ограничен настоящим file I/O и общими codec; он пригоден для будущего coordinator без фиктивного sync_directory.

Перед включением SST в пользовательскую базу нужно выбрать публикацию по ADR0014. Ни browser batch, ни освобождение WAL/memtable, ни destructive GC этот ADR не вводит. Файловый слой не экспортируется из публичного `hoke/db`; Worker protocol2 и существующий OPFS WAL layout не меняются.
