# ADR 0002: файловый слой, WAL и граница подтверждения записи

Статус: принято для экспериментального WAL-only прототипа, 27 октября 2026. Пользователь выбрал вариант B — бинарный WAL с CRC32. Реализованы файловый фундамент, codec, Engine и recovery.

## Цель ближайшего вертикального среза

`put(key, value)` → WAL → успешная синхронизация → обновление памяти → подтверждение. После остановки процесса `open` восстанавливает подтверждённые записи. `delete` добавляет tombstone; ключи и значения — байты, ключи упорядочены лексикографически без locale/Unicode normalization.

Это будущий WAL-only прототип на обычной файловой системе. SSTable, compaction, транзакции, WASM и native bindings в него не входят. Пока нет стабильного файлового формата или обещания production-ready.

## Что можно реализовать до выбора формата

Cargo workspace и crate `stowtree-core`, без сторонних зависимостей. Синхронный Storage trait с явными offsets: len/is_empty, read_at, write_all_at, set_len, flush, sync_all. Адаптеры памяти и обычного файла выполняют одинаковый байтовый контракт.

- read_at разрешает короткое чтение; на EOF возвращает 0.
- write_all_at либо записывает все байты, либо возвращает ошибку. Ошибка может оставить частичный префикс; автоматический rollback не обещается.
- write за EOF и set_len при расширении заполняют пробел нулями. Пустая запись не расширяет файл.
- Переполнение offset + length отклоняется до записи.
- FileStorage открывает/создаёт файл без truncate, запрашивает эксклюзивный неблокирующий lock. Второй согласующийся писатель получает ошибку.
- Lock кооперативный: внешний код, обходящий lock или удаляющий файл, не входит в гарантии. Нельзя считать file lock готовым протоколом владения каталогом LSM.
- MemoryStorage — явно выбранный volatile backend, а не резервный путь при ошибке файлов.
- Блокировка удерживается до закрытия владельца. Ошибки open/read/write/metadata/sync передаются вызывающему коду.

Текущая проверенная среда: Rust 1.97.1, Linux. В Cargo указан нижний API baseline 1.89 для std file locks; отдельной проверки MSRV и других ОС пока нет.

## Выбор формата WAL

| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. | B. Нужна явная совместимость формата.                                            |
| C. Готовый codec для записей + собственный WAL framing | Меньше ручного encoding полей, удобно развивать Rust-типы                                                                       | Codec не решает durability и framing; появляется зависимость и вопрос стабильности wire format. Больше неявной связи с сериализатором.                                                  |

Выбрано B, бинарный WAL с проверкой заголовка и payload. Формат проекта ещё не выпущен; незачем сначала вводить JSON-формат, который придётся выбрасывать при переходе к byte keys/values.

Точная спецификация: [WAL v1](../WAL_FORMAT.md). Есть magic + независимая версия файла, monotonic sequence number, put/delete tag, длины ключа/значения, checksum заголовка до allocation и checksum содержимого. Размеры проверяются до выделения памяти. После выбора добавлена зависимость crc32fast 1.5.3, закреплённая Cargo.lock вместе с cfg-if; serde не используется. CRC проверяет случайные повреждения, не является криптографической защитой.

## Рекомендованная durability для первого прототипа

Один синхронный писатель. На каждой операции:

1. Проверить входные размеры и sequence overflow.
2. Закодировать полную запись до изменения хранилища.
3. Добавить frame в WAL, завершив все short writes.
4. Вызвать flush, затем sync_all; ошибки не подавлять.
5. Только после успеха изменить memtable и вернуть Ok.

Это медленнее batching, зато начальный контракт понятен. Group commit и режим без sync добавлять позднее после измерений. При ошибке I/O экземпляр становится непригоден для новых записей до закрытия и recovery: нельзя дописывать после неизвестного частичного frame.

Ошибка или потеря ответа не гарантирует отсутствия записи после restart: байты могли сохраниться, но подтверждение не дошло. На такой ошибке результат операции считается неизвестным, а не откатившимся. Нельзя автоматически повторять неидемпотентное действие без проверки.

Для нового WAL недостаточно sync_all файла: долговечность имени требует отдельной политики создания/синхронизации родительского каталога. До её реализации заявляем проверку повторного открытия/process crash существующего файла, не полную устойчивость к потере питания на произвольной ОС/ФС.

## Предлагаемая политика восстановления

- Проверять magic/version до чтения records. Неизвестную версию не открывать и не перезаписывать.
- Восстанавливать только полностью проверенные frames в sequence order.
- Проверять lengths и header checksum до allocation и payload parsing.
- Незавершённый append в самом конце журнала рассматривается отдельно от checksum mismatch и нарушения sequence.
- Полная запись с неверным checksum, неизвестный op, недопустимые lengths или sequence gap — ошибка corruption с offset; не пропускать произвольные bytes и не искать следующий magic.
- Для оборванного EOF tail сохраняется проверенный префикс. Tail считается неполным, когда осталось меньше 28 байт header либо проверенный header объявляет frame, который выходит за EOF. После полной проверки префикса set_len укорачивает WAL до последнего frame, затем flush + sync_all. Полный header с неверным CRC не считается безопасным хвостом. Частичный заголовок самого файла не чинится автоматически.
- Recovery не должен потерять старые подтверждённые записи или молча очистить WAL.

## Критерии следующего шага после выбора

- API Rust: open, put, get, delete; `Result` с причиной I/O и offset повреждения.
- Roundtrip после закрытия и повторного открытия; второй процесс читает те же данные.
- Пустые и бинарные ключи/значения, overwrite, tombstone, пограничные размеры.
- Golden fixtures encoding; плохие magic/version/checksums/lengths/sequences.
- Обрезание каждого byte offset последнего frame; повреждение посреди файла не считается tail.
- Инъекция ошибки write/flush/sync: нет ложного Ok, исходные confirmed keys восстанавливаются.
- Убийство дочернего процесса в контролируемых точках и повторное открытие. Тест не выдаётся за power-loss simulation.

SSTable и стратегия compaction требуют отдельного ADR перед их реализацией; не фиксируем их формат заранее.
