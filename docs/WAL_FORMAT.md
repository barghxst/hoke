# Экспериментальный формат WAL v1

Это версия бинарного файла Rust-движка, а не version React/JS стора и не версия npm-пакета. Формат пока не опубликован и не обещает долгосрочную совместимость. Неизвестная версия файла отклоняется без очистки или downgrade.

Все целые поля little-endian. CRC32 — IEEE, контрольный вектор `123456789` → `0xcbf43926`. Используется crc32fast. Checksums обнаруживают случайные повреждения, но не заменяют аутентификацию.

## Заголовок файла — 16 байт

| Offset | Размер | Значение              |
| ------ | ------ | --------------------- |
| 0      | 8      | Magic `STOWWAL\0`     |
| 8      | 4      | Версия файла, u32 = 1 |
| 12     | 4      | CRC32 байтов 0..12    |

Короткий заголовок файла — ошибка, автоматическая очистка не выполняется. Заголовок нового пустого файла записывается и синхронизируется перед операциями. Создание имени файла ещё не включает fsync родительского каталога.

## Заголовок каждой операции — 28 байт

| Offset | Размер | Значение                                               |
| ------ | ------ | ------------------------------------------------------ |
| 0      | 4      | payload_len = key_len + value_len, u32                 |
| 4      | 8      | sequence number, u64; первая запись 1, далее строго +1 |
| 12     | 1      | Операция: 1 = put, 2 = delete                          |
| 13     | 3      | Reserved, обязательно нули                             |
| 16     | 4      | key_len, u32                                           |
| 20     | 4      | value_len, u32                                         |
| 24     | 4      | CRC32 байтов заголовка 0..24                           |

Далее идут key_len байт ключа, value_len байт значения и trailer 4 байта — CRC32 полного 28-байтного заголовка вместе с payload.

Ограничения: ключ ≤ 64 KiB, значение ≤ 16 MiB. Пустые ключи и значения разрешены. Для delete value_len должен быть нулём. Put пустого значения отличается от delete по коду операции. В Rust значения — произвольные bytes, без кодирования строк, JSON или Unicode normalization.

Header CRC проверяется до использования длины для allocation. Проверяются reserved bytes, op, sequence, лимиты и согласованность payload_len. Затем ограниченный буфер payload/trailer читается и проверяется полный CRC. Golden fixtures со всеми байтами и контрольными суммами находятся в unit-тестах wal.rs.

## Подтверждение и неизвестный результат

Операция кодируется полностью, добавляется в WAL, проходит flush и sync_all. Только потом обновляется BTreeMap в памяти и возвращается Ok. При I/O-ошибке новые записи блокируются: нужно закрыть экземпляр и выполнить recovery.

После ошибки данные могли физически попасть в WAL. Recovery может показать такую неподтверждённую операцию, если frame полностью записан и корректен. Это не транзакционный rollback. Чтение от poisoned экземпляра показывает только последний опубликованный in-memory state; восстановленный state после reopen может быть новее.

## Восстановление

1. Проверить magic, CRC и версию заголовка файла.
2. Читать frames по порядку, полностью проверять их до применения в память.
3. Если до EOF осталось меньше 28 байт, это неполный финальный header.
4. Если header корректен, но frame не помещается до EOF, это неполный финальный payload/trailer.
5. Такой хвост удаляется после проверки всего префикса, затем вызываются flush и sync_all. Число удалённых байтов доступно через Recovery.
6. Полный плохой header, неверный payload CRC, нарушение sequence и неизвестная операция — corruption с offset. Файл не переписывается и не сканируется в поисках следующего frame.

Эта политика предполагает единственного кооперативного писателя и оборванный append при process crash. Потерю питания, физическое повреждение, удаление/подмену файла внешним процессом и все особенности файловых систем она не моделирует. Начало журнала с частичным заголовком не считается безопасно восстанавливаемым.

## Рост журнала

Каждая операция добавляет frame; delete записывает tombstone, старые версии остаются в файле. При open весь WAL перечитывается, текущие данные целиком находятся в памяти. Уменьшение файла, SSTable, manifest и compaction будут отдельным следующим шагом.
