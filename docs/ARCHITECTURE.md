# Как устроен Hoke

Hoke хранит данные локально, внутри приложения. В репозитории развиваются два пути: KV для небольших значений и DB с собственным файловым движком. Они имеют разные API и сейчас не используют общее хранилище.

## Два пути хранения

`hoke/kv` — синхронный TypeScript API со строковыми ключами. Адаптер хранит значения в памяти или localStorage. Стор поверх KV добавляет defaults, проверку значения, версию схемы и миграции. `hoke/react` подписывает компонент на snapshot стора. Для этого пути Rust, WebAssembly и Worker не нужны.

`hoke/db` предлагает `openDatabase` с типизированными JSON-коллекциями поверх низкоуровневого `openDB` с ключами и значениями `Uint8Array`. Порядок ключей — лексикографический по байтам. Он поддерживает упорядоченное чтение, диапазоны и пространства ключей. В браузере данные лежат в OPFS — файловом хранилище конкретного origin. Rust-движок выполняется в Worker через WebAssembly. Подписки DB пока сообщают только об изменениях через текущее соединение; `useDBValue` из hoke/react читает один типизированный документ и обновляет его после локальных commit.

Сохранение в localStorage не переносит значения в OPFS. Имена KV-сторов и DB-коллекций принадлежат разным API.

Для обычного приложения начните с [DATABASE.md](DATABASE.md): этот слой скрывает UTF-8/JSON-кодирование, выбор container-v1 и политику логического обслуживания. Ниже описан byte API, на котором он построен.

## Кто за что отвечает

```text
Приложение
├─ hoke/kv → Store → React hooks       TypeScript, память/localStorage
└─ hoke/db                            TypeScript, Promise API
   └─ Dedicated Worker                очередь запросов и владелец файла
      └─ hoke-wasm                    перевод JS-вызовов в Rust
         └─ hoke-core                 алгоритмы хранения и восстановления
            └─ Storage adapter        операции над байтами OPFS
```

Ветка KV показывает слои возможностей: приложение может использовать KV напрямую или добавить Store и React. Ветка DB показывает путь запроса. Результат DB возвращается обратно через Worker, и только после успешного ответа клиент уведомляет подписчиков.

| Слой           | Обязанность                                               | Чего он не определяет                     |
| -------------- | --------------------------------------------------------- | ----------------------------------------- |
| DB client      | Публичные методы, проверка аргументов, подписки           | Формат долговременных файлов              |
| Client session | Идентификаторы запросов, ответы, timeout, abort, закрытие | Порядок записи WAL/SST                    |
| Worker         | Последовательная обработка запросов, владение OPFS handle | Алгоритм восстановления базы              |
| WASM bindings  | Преобразование аргументов, ошибок и пакетов байтов        | Самостоятельный протокол commit           |
| Rust core      | WAL, таблицы, чтение версий, batch, публикация и recovery | React, DOM, формат пользовательского JSON |
| Storage        | Чтение/запись по offset, truncate, flush/sync             | Семантика ключей и транзакций             |

Rust выбран, чтобы один движок можно было выполнять напрямую на обычной файловой системе и собирать в WASM для браузера. Будущий React Native адаптер сможет использовать тот же низкий интерфейс хранения; сейчас его нет. Сам по себе выбор Rust не обеспечивает сохранность — её определяют протокол записи, поведение файловой системы и проверки отказов.

## Из чего состоит ядро

`hoke-core` построен на стандартной библиотеке Rust и собственных кодеках записей; CRC32 считает небольшая зависимость `crc32fast`. Здесь нет встроенной SQLite/RocksDB. Основная map использует `BTreeMap`, tombstones WAL-only engine учитываются отдельно через `BTreeSet`. Интерфейс `Storage` скрывает платформенное чтение и запись файлов.

| Термин                    | Что это в Hoke                                                 | Зачем нужен                                                |
| ------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| WAL — журнал изменений    | Последовательные записи put/delete с длинами, sequence и CRC32 | Восстановить изменения после повторного открытия           |
| Memtable                  | Упорядоченное производное состояние в памяти                   | Быстро читать ещё не сброшенные изменения                  |
| Tombstone                 | Отметка удаления                                               | Не показать старое значение из предыдущей таблицы          |
| SST — sorted string table | Неизменяемая отсортированная таблица с индексом и проверками   | Читать сохранённые значения без загрузки всех values в map |
| Flush                     | Перенос текущих изменений из memtable в SST                    | Сократить активный WAL и текущую delta в памяти            |
| Compaction                | Слияние активных источников с выбором последних версий         | Убрать логически устаревшие записи и покрытые удаления     |
| Commit root / manifest    | Список источников, составляющих опубликованное состояние       | Сделать новое состояние доступным целиком                  |

Это LSM-подобный движок: журнал → память → отсортированные таблицы → слияние. Сейчас нет уровней LSM, фонового планировщика compaction, Bloom filters и автоматического выбора небольших групп таблиц. Используется простое полное слияние. Полные индексы ключей остаются в памяти; payload limits не являются ограничением всей RAM процесса.

CRC32 помогает обнаруживать повреждение записей. Это не шифрование и не защита от намеренной подмены данных.

## Три координатора над общими форматами

В ядре существуют три рабочих варианта, и их протоколы нельзя смешивать:

| Rust API               | Хранение                                        | Как публикуется изменение                         | Где используется                                 |
| ---------------------- | ----------------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| `Engine<S>`            | Один WAL и производная map                      | Запись frame и sync до обновления map             | Browser `wal-v1`, WAL CLI/тесты                  |
| `Database<D>`          | Каталог: WAL, SST, manifest                     | Подготовка файлов и атомарная публикация manifest | Native CLI и тесты файловой системы              |
| `ContainerDatabase<S>` | Один append-only контейнер с WAL/SST сегментами | Новая запись root в журнале commit                | Browser `container-v1`, native container example |

Они разделяют форматы WAL/SST и алгоритмы чтения. Native `Database` умеет удалять obsolete файлы после публикации; контейнерный вариант пока оставляет исключённые сегменты в том же файле.

Контейнер выбран для OPFS, чтобы публикация состояния не зависела от недоступного здесь sync каталога. Browser DB не запускает native manifest-протокол. Один файл принадлежит одному владельцу; совместной маршрутизации между вкладками пока нет.

## Путь записи в container-v1

Например, приложение вызывает `writeBatch` для двух ключей:

1. TypeScript проверяет размеры, копирует входные байты и отправляет запрос Worker. Отдельная копия ключей остаётся для уведомлений после ACK.
2. Worker последовательно обрабатывает запрос и вызывает `WasmContainerDb`.
3. Rust проверяет batch и готовит WAL payload до persistent I/O. При достижении лимита может сначала сбросить прежнее состояние.
4. В контейнер дописывается immutable WAL segment. Сам append ещё не публикует batch.
5. Journal синхронизирует сегменты, дописывает root со ссылками на активные SST/WAL и снова запрашивает синхронизацию.
6. После успешного commit координатор обновляет производную memtable. Worker отправляет ACK; клиент завершает запрос и уведомляет подходящих подписчиков.

Если ответ потерян между commit и ACK, приложение не знает исхода, хотя запись могла сохраниться целиком. Abort после dispatch завершает Worker, но не отменяет уже опубликованный root. Нужно открыть базу снова и проверить состояние. Ошибка callback подписчика происходит после сохранения и возвращается с `committed: true`.

## Как читается значение

Сначала проверяются текущие изменения в памяти. Если ключ там удалён, возвращается отсутствие значения: старые SST больше не рассматриваются. Иначе поиск продолжается от новой таблицы к старой. Scan объединяет упорядоченные источники, выбирает последнюю версию каждого ключа и исключает tombstones.

При `flush` появляется новая SST с текущими изменениями и удалениями. Root включает её и исключает прежние WAL segments; после commit memtable очищается. `compact` объединяет все активные SST и текущие изменения в максимум одну новую SST. Так как старые версии исключаются целиком, покрытые tombstones можно удалить.

Контейнер остаётся append-only: логическая очистка не возвращает место файловой системе. Для физического уменьшения файла нужен отдельный будущий протокол.

## Что происходит при открытии

Journal проверяет внешний формат, последовательность записей, CRC и допустимость ссылок root. Координатор проверяет активные таблицы и immutable WAL payload, восстанавливает memtable из WAL, перечисленных в последнем опубликованном root. Полные значения SST не загружаются в map; чтение их payload и соответствующая проверка выполняются по запросу.

Физически неполный EOF-хвост можно отбросить только после проверки активных данных. Полная повреждённая запись вызывает ошибку; отката на старый root или молчаливого fallback нет. Ошибка persistent I/O или источника может сделать соединение непригодным до повторного открытия.

Успешные локальные тесты и убийство процесса не доказывают поведение при потере питания, очистке данных origin или на всех браузерах. Точные границы протокола описаны в ADR и OPFS-документации.

## Версии относятся к разным вещам

| Версия                    | Что означает                                         |
| ------------------------- | ---------------------------------------------------- |
| KV Store `version`        | Схема значения приложения, например darkMode → theme |
| WAL/SST/container version | Долговременный бинарный формат движка                |
| Worker protocol           | Формат сообщений TypeScript ↔ Worker                 |
| Container `generation`    | Порядковый номер опубликованного commit root         |

Новая пустая container DB начинает с root generation 1. Последующие commit увеличивают счётчик; это не миграция пользовательской схемы. Миграции Store уже есть в KV. Миграции схемы DB и явный импорт прежнего WAL в контейнер ещё предстоят. Одинаковое имя в `wal-v1` и `container-v1` открывает два независимых файла.

Удобный document API находится в `document-database.ts` (open/composition), `document-contract.ts` (публичные типы), `document-session.ts` (общая очередь и maintenance), `document-collection.ts` (CRUD/batch), `document-codec.ts`/`document-range.ts` (JSON/UTF-8/границы). `open-byte-database.ts` сохраняет прежний openDB. React-хук находится в `react/db-value.ts` и импортирует только тип коллекции, без runtime DB/Worker зависимости.

Фасады `engine.rs`, `database.rs`, `sstable.rs` и `lib.rs` сохраняют публичные пути типов. Внутренние модули не становятся отдельным API. Большой файл разделяется по причине изменения: формат, чтение, commit, lifecycle, а не ради лимита строк. Связные модули и тестовые сценарии могут оставаться длиннее небольшого фасада.

Чтобы разобраться в одном действии, начните с `client.ts`, проследите запрос в `worker.ts`, соответствующий биндинг в `hoke-wasm` и метод `ContainerDatabase`. Для протокола сохранения читайте `container/journal`, для native варианта — `database/publication.rs`.
